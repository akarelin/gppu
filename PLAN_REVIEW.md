# gppu review

Goal: gppu does what it is meant to. gppufs and Linked Data are native to gppu, built on gppu's own configuration, logging, apps and primitives; each thing has one implementation; the documentation is generated from gppu's code alone. Nothing that works is dropped; backwards compatibility is not a constraint.

Alex's requirements (2026-10-18, deciding where Linked Data lives): Linked Data is a submodule of gppu, its base API for records in gppu; the locations API gppu already has serves it; it uses the primitives gppu already has, such as spans and paths; gppu's Postgres and ORM are improved, its unused ORM replaced by the one Linked Data uses; an API app is a type of gppu app. (2026-10-19): gppu is not rewritten and what works is kept; documentation is generated correctly; functionality spread over several files is put right; gppufs and Linked Data are native to gppu, not side modules that do not use it. (2026-10-20): gppu.py holds the environment, its configuration and the regular apps, and `app.py` the apps with steps; there is one environment, `Env`, and no second class doing the same. `y2path` is for anything with a slash in its name, not only a file system path, and stays so; `Path` is a child of `y2path` and `pathlib.Path`, the file system path. A parameter that is a slash path written as a string takes a string or a `y2path`. The configuration's Jinja is of two kinds, completely different: what is evaluated at startup, while `Env` loads the configuration, and what code evaluates at runtime; both stay, and gppu shows them as two. The configuration is in `Env`, and every object holds it in its `_my`; there is no State in gppu. Outside y2 `Env` is the global configuration and what apps look up (name, host, time zone, tracing); several apps in one environment is y2's. `gppu.app_service` holds `AppService`, an app that runs all the time and reloads its configuration from MQTT; what exists in gppu only for display-control lives there. `mixin_Rest`, the universal REST API to any object, works only in an async app and sits below `AsyncApp`; no gppu app includes it. The HTTP utilities only IoT uses stay in `gppu.iot`. YMRO, the init, load and start steps, stays in gppu: any app, synchronous or asynchronous, may need steps to finish before it starts; `Env` has an initialization cycle too, and both `Env` and the apps use YMRO. There is one YMRO, Alex's; an asynchronous step method takes `@sync`. Regular apps do not use the stepper, `App` and `CliApp` among them; async apps and every service that starts do, an API among them, and a class that needs the stepper composes `_App` with `mixin_Stepper`. Anything that has `_Config`, such as `_Base`, has `Env` loaded by the time it exists, and its `_my` is a copy of it. A program says what it is through `APP`, a dictionary of key-value pairs every program has from the import, from which its environment is created: its name, its configuration, whether it needs the topology (the nearest `_config/config.yaml` upward), whether its command line overrides its configuration, and the log's file and trace rules. The command line then overrides the configuration, the data and the log's parameters alike, and that is all: a full CLI app, with a schema, is not gppu's: `--key value` sets a key and a bare `--flag` sets it to True; there is no `=` form. A program without a configuration file runs on its command line alone. `init`, `load` and `start` never take parameters. The environment is built up from module to module into one object: the basic environment in gppu has the operating system, the path builder and the log, and `Env` adds the app's configuration and the app's log; its methods are promoted to module names, so code calls `Info` or `glob` and never sees the class, and there is no separate logger class. `Env` is an app of a special kind, static, global and one per program, and it has the same parent as the apps: they share its members, `my` and the log among them, without repeating them, and stay separate objects; an app is made from another app by copying it, and from the environment the same way. Any program that imports gppu is already an app; `App`, `CliApp` and `AsyncApp` stay for programs that need more, such as their own configuration or async. The log is `Logger`, with the calls a program uses to reconfigure it, and `mixin_Logger` gives a class its log. Importing gppu gives a program its environment, which it never needs to know of: `Info`, `Warn`, `glob` and the rest go through `Env`, and an app works as such a script does, its init being the environment's: the first read of the configuration loads it from beside the program. Logging works from gppu's first lines: a bootstrap of a couple of lines gives a plain console log, and colours, trace rules and the file mirror come on top of it. The Vault is its own module, `gppu.vault`, built on `dict_from_yml`: importing it adds `!secret` to the YAML it reads, and an environment variable overrides a secret. An app gives its part of a step by overriding the regular `init`, `load` or `start` and calling super; the double-underscore parts are for rare cases. The three steps are: init does light loading, what can be loaded and parsed, as a constructor does; load does the heavy loading of data; start comes last, and at its end the callbacks and timers start working. (2026-10-20, handlers): a handler is a universal way to get information about a file or a folder. The type of a file is not known in advance: probing is given a path, and that suffices to figure out which handler to use. Probing comes before indexing. Probing is done in fsspec's `info`, and the same probe can be called alone on any path. Probe called alone on a path gives what info gives. Handlers do not do probing: probe takes the path and the stat info has already taken, and from the stat says an ignored folder, a junction, a link, an offline file, a folder or a file, and from the path everything else, such as a session folder; a file's handler is told by its extension. A path probe has told is ignored, a link, a junction or an offline file without a handler, since nothing is read from it. Parse is the method handlers use to get information from a file, and every handler describes what it returns. Probe and handlers return one record class, Linked Data's record: a file has created and updated as every record does, and what is metadata is in meta, not data; there is no source. Probe starts from the stat. Time is always local. A handler reads a time one way, and says which time it reads, a start, an end or a moment. The log handler reads only as much as it needs for its first time and its last. gppufs is the primary user of probing, and probing runs on a path directly, without gppufs. gppufs has a file system's interface, and handlers, which work with files, speak the language of the file system and of gppufs: `ls` lists a folder, and `info`, the file system's standard method, gives what is known of a path without reading it, so that calling it on a folder never reads what the folder holds. A Linked Data record is universal and stores anything. The catalog is a different thing. Every handler is registered with probing, so probing knows every handler there is; probing is not a class, and not the handlers' class, and its name is still to be Alex's. Probing runs in a very small, finite time: what it needs from a handler is cheap, and it does no more than the minimum it needs to find the handler; it is asynchronous, since on a file share it can take seconds, and it never returns what a handler gives, such as a session's turns. Every type of data has one handler class, not a data class beside a handler, and a handler's parsing is one method, asynchronous; a handler parses, and its result is not the handler. Handlers have types and subtypes, and return records compatible with Linked Data's. A handler keeps what stat gives as stat gives it. Every name in the handlers is one Linked Data's documentation uses, read correctly. A handler handles records. A session consists of messages; turns are a statistic of a session. Handlers depend neither on gppufs nor on fsspec. The part of Linked Data responsible for files and folders, and its sessions, use handlers: one calls the other, and there is no second copy of a handler's reading anywhere. What Linked Data lacks is noted, not changed. The status line works with sessions through the handlers, and so does the program that saves a session to a file.
